The purpose of Stage 2 is to address the #1 issue identified in the diagnostic:

DASHBOARD QUERY FAN-OUT.

The diagnostic found that Dashboard rendering performs repeated database reads for individual sessions, placements, students, DailyLogs, point events, and progress information.

I want to reduce those repeated database calls WITHOUT changing Dashboard behavior or any underlying business logic.

### PRIMARY GOAL

For a selected Dashboard date, efficiently batch-load the records needed to construct the Dashboard rather than repeatedly querying the database separately for each individual Dashboard card or placement.

Where practical, retrieve the necessary:

- Sessions
- Placements
- Students
- DailyLogs
- Point events
- Progress/completion information

in efficient grouped/batched queries and reuse those results while rendering the Dashboard.

The Dashboard should produce exactly the same result as it does now.

### IMPORTANT DESIGN PRINCIPLE

This is a DATABASE ACCESS optimization, not a rewrite of Grotto business logic.

Existing functions that determine:

- attendance
- periods served
- points
- completion
- placement status
- make-up requirements
- scheduled dates
- future-date behavior
- referrals
- partial days
- absence behavior

should continue to produce the same results.

If replacing an existing per-record function with batched data would require duplicating or substantially rewriting important business logic, STOP and report that issue rather than making a risky change.

`db_manager.py:3073–3089`

`app.py:3907–4138`
